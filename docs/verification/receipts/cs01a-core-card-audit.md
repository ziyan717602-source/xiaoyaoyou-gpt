## 范围与规则证据

- 机器合同冻结鼠儿果、天雷破、冰心诀和灵葫仙丹的普通、响应、救援与跨系统模式，共 12 项验收条件。
- 数据库 `Tux` 的四行与 `JP06.cs:338-519` 确认：鼠儿果指定一人补 2；天雷破普通模式指定一人造成 2 点雷伤，另有事件目标模式；冰心诀取消当前等待中的牌效果；灵葫仙丹普通模式只回复本人 2 点，濒死模式回复当前 0 HP 目标 2 点。
- `TP02Valid(type 0)` 恒真，所以满血使用仍合法、卡牌照常支付。普通模式作为技牌进入冰心诀响应链；救援模式继续使用已序列化的濒死优先权管线。
- 天雷破的事件模式、冰心诀对后续内容的响应、鼠儿果/灵葫仙丹的【净衣咒】联动均有明确后继切片。四个目录项继续保持 `partial`，没有用“当前独立模式通过”冒充整项 verified。

## 实现与验证

- 卡牌定义由单一 `coreAction` 扩展为普通 `heal-two` 加独立 `rescueAction`，同一张灵葫仙丹可在行动和濒死两个合法入口使用，两个入口不会互相误报。
- 普通模式只向当前行动者投影本人目标；外部伪造他人目标返回 forbidden。支付后创建可恢复的效果帧，响应全部放弃才按 `min(maxHp, hp + 2)` 回复；冰心诀通过则不回复。
- `npm run core-cards:verify`：合同 12/12；核心单元、JSON 重放、伤害/濒死回归与长局 Bot 15/15；真实网络生命周期 2/2。
- `npm run check:full`：unit 39/39、replay 12/12、bots 6/6、integration 7/7、Playwright 3/3、本地烟测 6 个客户端；构建、类型、格式与公开历史检查全部通过。
- `npm audit --audit-level=low`：0 vulnerabilities；`git diff --check`：通过。
- 六条真实 WebSocket 验证本人可见两张灵葫仙丹、其他五人看不到实例 ID；第一张被冰心诀抵消且 HP 不变，第二张全员放弃后回复到上限。JSON 测试在普通自疗响应窗口中序列化重启，恢复执行和逐事件重放均与不中断状态相同。

## 失败先行与审计记录

- CS00 初稿曾把 CS01A 描述为“四项逐一提升 verified”；读取 C# 后发现天雷破事件模式、冰心诀未来目标和【净衣咒】联动尚无上游系统，立即修正为逐模式验收并保留 partial，避免制造虚假完成率。
- 多模式建模审计发现把灵葫仙丹从 `rescue-two` 直接改成 `heal-two` 会破坏濒死入口；最终使用独立 `coreAction` / `rescueAction`，并让既有濒死网络用例继续回归。
