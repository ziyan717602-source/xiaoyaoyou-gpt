# 工程组织方法

状态：已接受；无人值守执行见根目录 `GOAL_CONTRACT.md`

## 结论

本项目不在 loop engineering 与 graph engineering 中二选一，而采用：

> **宏观有向工作图 + 微观有界验证循环 + 可追踪规则决策闸门**

“Loop Engineering”和“Graph Engineering”目前都是新兴方法名称，并非稳定行业标准。这里采用的是它们可检验的工程原则，不绑定某个自动化框架。

- Loop Engineering 关注目标、行动、观察、调整和明确停止条件；
- Graph Engineering 关注节点依赖、上下文边界、外部事实、证据与合法流转；
- 对本项目而言，工作图避免 AI 一次吞下三万多行规则，验证循环避免单次生成后凭感觉宣布完成。

参考：[IBM 对 Loop Engineering 的阶段与人类闸门说明](https://www.ibm.com/think/topics/loop-engineering)、[Agent Graph 对 Graph Engineering 边界的说明](https://github.com/context4ai/agent-graph/blob/main/docs/en/graph-engineering.md)。

## 三层图

### 1. 领域依赖图

表达规则原语之间的真实依赖，例如：

```text
命令与版本校验
  ├─ 效果身份与效果栈
  │    ├─ 响应窗口 ──► 冰心诀/拒绝/净衣咒
  │    └─ 伤害流水线 ──► 濒死批次 ──► 救援 ──► 死亡与胜负
  ├─ 玩家私密视图
  └─ 快照/事件重放 ──► 掉线重连 ──► 服务重启恢复
```

这张图决定迁移顺序。卡牌不能因为文件顺序或“看起来简单”就绕过依赖原语。

### 2. 工作契约图

每个可开发节点必须包含：

| 字段     | 内容                                       |
| -------- | ------------------------------------------ |
| 目标     | 一句可判定完成与否的结果                   |
| 前置节点 | 必须已经通过的契约                         |
| 规则证据 | C# 方法、数据库记录、联网说明和已确认裁定  |
| 允许范围 | 本节点允许修改的包和文件                   |
| 禁止范围 | 不能顺手重构的内容                         |
| 验收门   | 必须运行的确定性命令与场景                 |
| 产物     | 代码、场景、日志、覆盖率和决策记录         |
| 停止原因 | 完成、规则争议、重复失败、超范围或预算耗尽 |

只有前置节点为绿色、规则证据齐全的节点才能进入实现。

### 3. 单节点验证循环

```text
读取节点契约与最小上下文
→ 先固定 C# 行为场景/失败测试
→ 实现最小改动
→ 运行静态检查、场景和属性测试
→ 独立检查实现与证据
→ 绿色：生成验证收据并结束
→ 红色：带原始失败证据返回下一轮
```

循环必须有边界：

- 连续三轮出现同一失败原因时停止并诊断；
- C# 行为存在歧义或明显不合理时，交互开发可提问；无人值守执行按自主裁定策略记录后继续；
- 不允许为变绿而删除、放宽或改写已经审定的验收场景；
- 单节点循环不自动合并到 `main`；只有总验收全绿后才可快进目标分支；
- UI 主流程和规则裁定必须有浏览器轨迹、可重放场景或决策记录，不由 AI 的“看起来正确”代替。

## Maker / Checker

未来可以让 AI 分工，但不是无约束的多 Agent 自由讨论：

- Maker 只获得节点契约、相关源码与失败测试，负责实现；
- Checker 读取规则证据、差异和测试产物，专门寻找绕过测试、隐私泄露和恢复缺口；
- Checker 不以 Maker 的解释为事实，只认可外部可重放证据；
- 规则场景最好先由独立步骤固定，再交给 Maker，降低同时修改实现和标准的风险；
- 最终合并由 `GOAL_ACCEPTANCE.md` 的客观闸门决定；维护者的后续审查是可选改进，不阻塞无人值守目标。

## Git 工作方式提案

- `main` 始终保持可构建和可测试；
- 一个工作图节点对应一个短分支和一个可审查提交序列；
- 并行节点使用 Git worktree 隔离，只有没有写入冲突且依赖已满足时才并行；
- PR/合并记录附带验证收据：命令、结果、随机种子、场景编号和未解决问题；
- 规则证据与测试先于或至少独立于实现提交，避免历史无法看出标准何时改变。

在第一个纵向切片之前，不安装额外自动循环框架，也不编排无边界自治多 Agent；先用两到三个准备节点与一个小 `/goal` 试运行完整流程，验证契约是否足够清晰。
