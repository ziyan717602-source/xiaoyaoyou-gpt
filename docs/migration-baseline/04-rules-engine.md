# 规则状态机

## 状态骨架

```text
MatchState
├─ schemaVersion / rulesetVersion / version
├─ phase / step / activePlayer
├─ players（完整权威数据）
├─ zones（牌堆、弃牌、场上区域）
├─ effectStack[]
├─ reactionWindow?
├─ pendingChoice?
├─ priorityCursor
└─ rng（种子与当前位置）
```

`MatchState` 只能包含数据，不能包含闭包、Promise、定时器或类实例方法。

## 规则处理结果

每次引擎推进直到出现以下边界之一：

- `resolved`：当前效果完成；
- `need-choice`：等待一个或多个玩家选择；
- `open-reaction-window`：允许合法玩家响应或放弃；
- `push-effect`：压入子效果；
- `replace-effect`：替换、重定向或修改现有效果；
- `cancel-effect`：取消指定效果实例；
- `game-over`：产生最终胜负。

## 效果身份

每个效果必须有稳定 `effectId`，并记录：

- 来源玩家、卡牌或技能；
- 父效果 `parentEffectId`；
- 目标与参数；
- 当前步骤；
- 可修改、可取消和已应用的状态；
- 创建它的领域事件序号。

冰心诀不能只修改一个全局布尔值；它必须引用要取消的效果实例。净衣咒等效果可以替换目标或替换结算方式，同时保留原效果链供日志与回放展示。

## 响应窗口

响应窗口包含：

- 稳定 `windowId` 和对应 `effectId`；
- 合法响应者顺序与当前优先权；
- 已放弃、已响应和仍待处理的玩家；
- 允许的动作类别；
- 截止策略，但不在规则层保存墙钟时间；
- 结束后的续算位置。

客户端提交过期 `windowId` 或错误版本时，服务端必须安全拒绝而不改变状态。

## 伤害与濒死流水线

```text
创建伤害意图
→ 伤害前修正/免疫/转移
→ 应用 HP 变化
→ 伤害后触发
→ 收集 HP ≤ 0 的存活角色
→ 打开濒死救援窗口
→ 逐次救援并重新计算名单
→ 无法救援者进入死亡结算
→ 胜负检查
```

多人同时濒死必须共享一个明确的结算批次，不能通过遍历顺序偶然决定谁先死亡。

## 确定性要求

- 相同初始状态和命令序列必须得到字节语义等价的结果。
- 洗牌只使用注入的伪随机数状态。
- 字典遍历、目标排序和同时触发项必须定义稳定顺序。
- 规则测试不得依赖系统时区、语言区域或机器速度。
