# 技术路线复核

状态：探针前路线已接受；具体库与生产冻结取决于三个探针

## 先确认真正约束

技术路线必须同时满足：

- 固定六人、标准包与“凤鸣玉誓”扩展；
- 复杂嵌套响应、多人濒死和隐藏信息；
- 任何等待点可序列化、掉线可恢复、服务重启可续算；
- PC 与手机浏览器共用服务端规则；
- C# 行为是默认规则依据，但疑似不合理时可以人工裁定；
- 本地开发先形成可靠证据，之后才部署云端；
- AI 可以加速迁移，但不能同时控制规则标准、实现和验收结果。

## 候选路线

### A. 保留旧 C# 服务端，加 Web 网关

优点：最短时间看到浏览器连入旧游戏；旧规则表面上无需迁移。

问题：阻塞输入、线程调用栈、一房间一进程、字符串协议和不完整重连状态全部保留。网关只能转换 TCP/WebSocket，不能解决服务重启恢复、可测试性和复杂 UI 协议耦合。

结论：只适合作为短期行为预言机，不作为生产路线。

### B. .NET 8 自研规则引擎 + TypeScript 客户端

优点：C# 语义和旧方法更接近；强类型、服务端性能和工具链成熟。

问题：旧代码仍不能逐行搬运，控制流必须重写；前后端两套语言与 Schema；AI 每次迁移需要同时理解 C# 旧实现、新 C# 状态机和 TypeScript UI。

结论：如果长期维护者明显以 C# 为主，这是可靠备选；它不会降低最关键的规则建模难度。

### C. TypeScript 自研规则引擎 + TypeScript 客户端

优点：协议、状态类型、测试 Bot、Playwright 和前端共享一个生态；适合按小节点迁移；fast-check 等状态序列工具可直接作用于引擎和网络层。

问题：所有 C# 效果都需要语义迁移；必须严格处理运行时 Schema、整数约束和包边界；不能因为“前后端同语言”就把权威规则放入客户端。

结论：当前推荐路线。优势来自验证闭环和共享契约，不是 JavaScript 本身更适合写规则。

### D. boardgame.io 作为规则内核

优点：自带回合、阶段、多人同步与房间基础能力。

问题：本项目仍需在其 phase/stage 之外实现效果身份、嵌套响应栈、替换/取消和可持久化续算；最终会形成框架状态机与自研状态机的双重控制。

结论：不采用为规则内核，也没有必要只为大厅功能引入。

## 推荐架构保持不变，但收紧边界

```text
packages/engine
  纯确定性状态推进，无网络、数据库、真实时间和 UI

packages/protocol
  命令、消息、运行时 Schema 与版本策略

apps/server
  每局单线程 Actor、WebSocket、定时器、事件/快照持久化

apps/web
  玩家视图、可用动作渲染、响应式交互
```

核心接口不是“调用某张卡的方法”，而是：

```text
applyCommand(state, command) -> newState + domainEvents
projectPlayerView(state, playerId) -> redactedView
resume(state) -> resolved | pendingChoice | reactionWindow | gameOver
```

服务端调度真实时间；引擎只接收 `TimeoutCommand`。每局命令串行处理，避免用锁修补并发规则。

## C# 行为预言机计划

不直接相信人工阅读就足够。正式迁移前先评估旧程序能否在隔离的 Windows 本地环境运行：

1. 固定旧源码、SQLite 数据库和程序集版本及校验值；
2. 尝试只构建实际需要的旧大厅、服务端和命令行客户端，缺失的 UI 项目不进入预言机；
3. 用六个脚本客户端驱动旧 TCP 协议，记录输入、公开广播、私密消息和最终状态；
4. 对同一种子/同一命令序列重复运行，标记旧实现本身不确定的部分；
5. 无法黑盒触发的复杂技能，建立带源码位置的人工黄金场景；
6. 如果旧行为明显异常，生成规则问题，不擅自把异常固化为新规则。

旧程序只在测试环境中运行，不接入新生产服务，也不成为新客户端的在线依赖。

## 开发前的三个技术探针

在迁移正式卡牌前，只做三个可丢弃或可保留的小探针：

### Probe 1：嵌套续算

人工构造“卡牌效果 → 冰心诀窗口 → 取消/全部放弃 → 恢复原效果 → 濒死 → 救援”的最小状态机。要求每一步 JSON 往返后结果一致。

### Probe 2：六连接与隐私

六个无头客户端加入本地房间，验证版本、幂等、六份不同玩家视图，以及公开提示不泄露谁持有反制牌。

### Probe 3：恢复与时间

在响应窗口中关闭服务，重新启动后恢复；模拟 15 秒行动时限、60 秒断联状态和强制选择的可重放随机合法项，确认超时作为命令进入日志并可重放。

三个探针都通过后，才把标准包卡牌接入真实迁移图。探针失败时允许调整技术路线，不背负已经迁移的大量内容。

## 当前不做技术承诺

以下选择推迟到探针提供证据后：

- HTTP 服务框架、ORM 和状态管理库；
- Redis、消息队列、Kubernetes 和多区域；
- 通用规则 DSL 或可视化规则编辑器；
- 自动 Loop/Graph Agent 编排框架；
- LLM 玩家、排位、观战和云厂商；
- 大规模 UI 动画和最终美术管线。

这能避免工具选型先于问题证据。
