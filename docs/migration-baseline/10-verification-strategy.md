# 验证与测试策略

状态：已接受；具体阈值由技术探针验证

## 总原则

浏览器测试、引擎模拟和 AI Bot 不是替代关系。它们发现的问题不同，正确做法是按成本和确定性分层：

```text
少量：本机真实浏览器与人工体验
      Playwright 六玩家关键流程
      服务端/WebSocket/恢复集成测试
      六玩家无头策略 Bot 长局模拟
大量：规则场景、属性测试、纯函数单元测试
```

越靠下运行越频繁；越靠上越接近真实用户，但更慢、更容易受环境影响。

## L0：静态契约

每次修改都运行：

- TypeScript 严格类型检查；
- 协议与持久化结构的运行时 Schema 校验；
- 格式、依赖边界和禁止导入检查；
- 数据清单完整性检查：编号唯一、引用存在、规则包归属正确。

静态检查只能防止结构错误，不能证明规则正确。

## L1：C# 行为场景与黄金样例

每张卡牌/技能先建立最小场景：

- 初始权威状态；
- 玩家命令序列；
- C# 代码与数据来源；
- 预期领域事件、最终状态和六个玩家视图；
- 超时、无目标、掉线或嵌套分支。

优先从旧服务端导出可机器读取的行为轨迹；无法自动运行的部分用人工复现并标记证据等级。怀疑 C# 行为不合理时，不把“修正版”偷偷写进黄金样例；交互开发生成规则问题，无人值守开发生成临时决策后继续。

## L2：属性与模型测试

除了示例，还要验证不变量：

- 同一初始状态、随机种子和命令序列得到相同结果；
- 牌和唯一实体不会无来源复制或消失；
- 过期、重复和越权命令不改变状态；
- 所有效果和响应窗口都有稳定身份与合法父子关系；
- 等待状态 JSON 往返后能继续得到相同结果；
- 玩家视图不包含无权看到的手牌与私密合法动作；
- 已结束的窗口不能再次接受响应；
- 合法命令序列不会让效果栈永久停留在不可推进状态。

建议使用 fast-check 生成命令序列并收缩失败样例。它的 model-based runner 支持同步、异步和受调度的异步命令，可用于状态模型和竞态验证：[fast-check Model Based Testing](https://fast-check.dev/docs/advanced/model-based-testing/)。

## L3：六玩家无头策略 Bot

这些 Bot 直接读取服务端提供的 `availableActions`，提交合法命令，不经过 DOM：

| Bot                | 用途                                         |
| ------------------ | -------------------------------------------- |
| `FirstLegalBot`    | 永远选择稳定排序后的第一项，保证可复现冒烟   |
| `AlwaysPassBot`    | 压测放弃、超时和无人救援路径                 |
| `CounterHappyBot`  | 只要能反制就反制，制造深响应链               |
| `RescueBot`        | 优先救援，覆盖多人濒死和目标变化             |
| `SeededRandomBot`  | 随机探索合法动作，失败可由种子重放           |
| `ProtocolChaosBot` | 发送重复、延迟、过期和越权命令，验证安全拒绝 |

目标不是让 Bot“会玩”，而是高速探索状态空间。失败产物必须包含规则集版本、种子、初始快照、完整命令日志和最小化后的重放用例。

## L4：服务端与恢复集成测试

在真实 HTTP/WebSocket 服务和临时数据库上验证：

- 六个连接加入同一房间；
- 命令串行化、版本冲突和幂等；
- 主动断线、网络抖动、晚到回复和重连；
- 响应窗口中服务进程重启；
- 从快照加事件恢复后与未重启分支一致；
- 15 秒行动超时、60 秒断联状态、自动放弃和可重放随机强制选择；
- 六个连接收到的玩家视图互不泄露。

此层不依赖浏览器，失败定位比 E2E 更直接。

## L5：Playwright 六玩家无头浏览器

Playwright 允许在一个测试中建立多个相互隔离的 BrowserContext，适合模拟六个独立玩家；官方也推荐不同角色使用独立 context/storage state：[BrowserContext 隔离](https://playwright.dev/docs/browser-contexts)、[多角色认证](https://playwright.dev/docs/auth#testing-multiple-roles-together)。

使用方式：

- 一个对局测试创建六个 BrowserContext，而不是六个页面共享 Cookie；
- 只覆盖关键用户旅程，不用 DOM 驱动数千局随机模拟；
- Chromium 作为日常主路径；发布前增加 Firefox、WebKit 与移动设备视口；
- 在失败重试时保存 trace、截图、控制台日志和服务端事件日志。Playwright Trace Viewer 可重放 DOM、网络和操作过程：[Trace Viewer](https://playwright.dev/docs/trace-viewer)。

首批浏览器场景：建房入座、六人准备、冰心诀响应、多人濒死救援、超时、掉线重连、手机完成同一选择。

## L6：本机真实浏览器体验验证

无头测试证明流程可执行，但不能充分判断牌是否看得清、响应链是否容易理解、手机点击是否顺手。

- 每个纵向切片完成后，用本机浏览器进行一次可见模式走查；
- 桌面至少验证常见 1366×768，手机至少验证 360×800；
- 信息层级、误触风险、提示语言和多人等待感受用布局断言、交互轨迹和独立视觉检查验收；
- 视觉快照用于发现变化；更新基线必须在收据中说明原因，不能只为消除失败盲目接受；
- 不需人工同时操作六个窗口：五名玩家由确定性 Bot 驱动，可见浏览器驱动被验收的视角。

因此，日常回归以 Playwright 无头六上下文为主；本机可见浏览器用于 UX 和最终验收，而不是二选一。

## L7：AI Bot 探索

LLM Bot 可以后加，但不能成为规则正确性的裁判：

- 只能从服务端给出的合法动作 ID 中选择，不能直接构造任意协议；
- 用于探索人类式长程选择、奇怪组合、提示歧义和 UI 文案理解；
- 输出不稳定，默认放在夜间或人工触发任务，不阻塞普通提交；
- 必须记录模型、版本、提示、温度、动作列表和完整对局日志；
- AI 认为结果“不合理”只生成待调查报告，不能自动修改规则或黄金样例；
- 早期没有稳定 `availableActions` 和重放系统时，不投入 AI Bot。

第一阶段的“机器人测试”应指确定性/随机策略 Bot，而不是 LLM 玩家。

## 测试频率

| 时机         | 必跑                                            |
| ------------ | ----------------------------------------------- |
| 本地每次提交 | L0、相关 L1、快速 L2                            |
| 合并请求     | 全部 L1/L2、L4、关键 Chromium L5                |
| 夜间         | 大规模 L3、竞态测试、浏览器矩阵、选择性变异测试 |
| 纵向切片验收 | 全层回归、L6 可见浏览器、恢复演练               |
| 云端发布前   | 长时运行、真实网络条件、备份恢复和部署回滚      |

当规则测试数量稳定后，可对核心引擎选择性使用 StrykerJS 变异测试，检查测试是否真的能杀死错误实现，而不只是覆盖了代码行：[StrykerJS](https://stryker-mutator.io/docs/stryker-js/introduction/)。

## 验证收据

每个工作图节点结束时保存：

- 节点和规则场景编号；
- Git 提交；
- 执行命令与退出码；
- 随机种子及最小失败序列；
- C# 行为证据或可追踪规则决策；
- 六玩家私密视图检查结果；
- 浏览器 trace/截图路径（如适用）；
- 尚未覆盖的风险。

AI、开发者和 CI 都只能凭这份证据宣布节点完成。
