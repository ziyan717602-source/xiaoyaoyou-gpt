# 规则权威与证据

## 权威顺序

迁移过程中遇到冲突时，按以下顺序处理：

1. 经项目维护者确认的迁移裁定记录；
2. 旧 C# 服务端的实际行为；
3. 旧联网版技能/卡牌说明中的明确联网描述；
4. 线下规则与卡面原文；
5. 注释、个人笔记和无法复现的历史说法。

原因：旧联网版已经针对提示复杂度、隐藏信息和难以实现的预见性规则做过调整，不能假设线下文字永远覆盖联网行为。

## 每项规则的迁移记录

每个技能或卡牌至少记录：

| 字段           | 含义                                              |
| -------------- | ------------------------------------------------- |
| `code`         | 稳定编号，如 `TP01`                               |
| `name`         | 展示名称                                          |
| `legacyOccurs` | 旧事件代码与优先级                                |
| `source`       | 文档、数据库和 C# 方法位置                        |
| `onlineRuling` | 新联网版的规范行为                                |
| `privacyNotes` | 是否可能泄露手牌或可响应能力                      |
| `edgeCases`    | 嵌套、多人、无目标、超时、断线等                  |
| `tests`        | 对应自动化场景编号                                |
| `status`       | `unreviewed / specified / implemented / verified` |

## 争议处理

- C# 行为是默认迁移结果；不因为实现者觉得“奇怪”就自行修正。
- 如果 C# 行为疑似 Bug、不公平、与说明明显冲突或无法稳定复现，交互开发时可暂停该节点向维护者提问；无人值守 `/goal` 时按 [GOAL_CONTRACT.md](../../GOAL_CONTRACT.md) 作出 `provisional-autonomous` 决定并继续。
- 提问必须包含：最小初始状态、操作序列、C# 代码位置、实际结果、不合理之处和两到三个可选裁定。
- 不在代码评审中临时猜规则；先增加一个裁定条目。
- 同一局中不能因为客户端版本不同出现两种规则。
- 修正规则时提升规则集版本；历史回放继续使用开局时锁定的版本。
- 无法确认时选择最接近旧联网行为、最少泄露隐藏信息且可稳定测试的方案，并标记待复核。

规则节点等待最终复核时，可以继续与它没有依赖关系的工作。无人值守的临时裁定必须带独立场景、决策记录和规则集版本，不得只在实现中留下隐式分支。

## 隐藏信息原则

- 服务器知道完整状态，玩家视图只包含该玩家有权知道的内容。
- 客户端不能通过“是否弹出响应框”、响应时间差或错误信息推断其他人的手牌。
- 反制窗口可对所有规则上可能响应的玩家显示统一状态；服务端只接受真正合法的命令。
- MVP 不提供观战入口或观战视图；诊断使用受控日志与离线回放。
