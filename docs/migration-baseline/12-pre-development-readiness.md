# 正式开发前准备闸门

状态：执行中

本文档定义 `xiaoyaoyou-gpt` 进入正式规则迁移前的 Definition of Ready。目的不是永久停留在设计阶段，而是用少量可丢弃的证据工作，阻止第四次在技术路线、规则模型或 UI 上整体返工。

本文档保留闸门的设计理由；实际执行和状态以根目录 [PREPARATION_CHECKLIST.md](../../PREPARATION_CHECKLIST.md) 为唯一总清单。

## 什么叫“正式开发”

以下任何一项开始前，所有硬闸门都必须通过：

- 批量迁移标准包或“凤鸣玉誓”卡牌、角色和技能；
- 将服务端架构、持久化格式或客户端组件当作生产实现继续扩展；
- 创建公开远程并推送当前历史；
- 围绕未验证的抽象开始多 Agent 或长循环自动实现。

为验证路线而编写的三个小型技术探针属于准备工作。它们必须有时间盒、清晰的通过条件，并允许失败后删除或改换路线。

## R-01：公开仓库与不可逆历史

已确定 GitHub 仓库名为 `xiaoyaoyou-gpt`，但现在不应直接推送。当前本地历史包含约 1,085 个 Git LFS 对象，包括图片、音频、DLL、数据库和文档。

已确认的公开边界是：

- 公开：新项目代码、自有分析文档、无第三方限制的测试数据；
- 本地保留：完整 `reference/psd48-master`、原始数据库、图音、DLL 和未核验文档；
- 公开证据：必要时仅提交来源位置、校验值和自有的行为轨迹，不复制原始素材。

首次推送前必须生成干净历史或分离公开仓库。对已跟踪文件新增 `.gitignore` 规则无法清除历史。清理前必须先保存可验证的本地历史备份，并确认参考源码仍留在本机；创建远程和推送仍是后续独立步骤。

通过标准：用 `git ls-files`、`git lfs ls-files` 和敏感信息扫描生成首次推送清单；清单中的每一类文件都有“可公开/不公开/待证明”结论。

## R-02：C# 行为预言机

当前环境诊断（2026-08-18）：

- 已安装 .NET 9 SDK，但旧项目面向 `.NET Framework 4.0`；
- 未发现 Visual Studio MSBuild/Build Tools；
- 本机 `.NET Framework 4.0` 引用目录只有语言资源，缺少 `mscorlib.dll` 等完整引用程序集；
- 对 `PSDBase/Base.csproj` 的隔离输出构建因缺失 .NET Framework 4.0 引用程序集失败，没有修改旧源码；
- 整个旧解决方案还引用缺失的项目，因此目标是只构建预言机必需的最小子集。

准备时先建立一份可重复的 Windows 工具链说明，然后按 `PSDBase → PSDClientZero/PSDGamepkg → 六个脚本客户端` 逐级验证。不为了得到完整 WPF 界面而修复与行为轨迹无关的旧项目。

止损条件：如果完整一个工具链时间盒后仍无法驱动最小对局，不继续漫无边界地修旧客户端。降级为“C# 源码位置 + 数据库记录 + 人工黑盒录像/日志 + 自主临时裁定”，并在每个黄金场景上标记证据等级。

## R-03：规则集目录

`reference/docs/scope.md` 是之前尝试留下的范围提案，不是当前规则权威。它与已确认产品决策至少有三处不一致：

- 它要求 2/4/6 人，当前范围已固定为六人；
- 它把回放列为不实现，但新引擎必须具备内部事件重放能力；这不代表 MVP 要提供玩家回放 UI；
- 它的“必须实现”复选框不是当前仓库的实现进度。

下一步不是直接导出数据库为 JSON，而是先建立一份可比对目录。每个条目至少包含：

| 字段              | 用途                                           |
| ----------------- | ---------------------------------------------- |
| `canonicalId`     | 新系统稳定 ID，不使用显示名作关联键            |
| `kind/package`    | 角色、卡牌、怪物、NPC、事件及标准/凤鸣玉誓归属 |
| `legacyIds`       | 数据库 ID/CODE、协议代码和 C# 绑定方法         |
| `dependencies`    | 依赖的结算原语、其它条目和 UI 选择类型         |
| `evidenceGrade`   | 可重放黑盒、源码+数据、纯人工或已裁定          |
| `ruleStatus`      | 已确认、有争议或待取证                         |
| `migrationStatus` | 未入图、已建场景、实现中、验证通过             |

通过标准：标准包和“凤鸣玉誓”的条目数量与数据库/C# 交叉核对完成，不一致全部进入问题清单，不用猜测补齐。

## R-04：先固定结算原语，后迁移卡牌

在写第一张真实卡之前，至少要对下列语义形成可执行场景：

- 效果、子效果、来源、目标、优先级和稳定身份；
- 响应窗口的开启、逐人放弃、再次响应、关闭和过期命令；
- 冰心诀的取消对象、可否嵌套反制及恢复原效果的位置；
- 单人与多人同时濒死、救援轮转、恢复、死亡与胜负检查时机；
- 伤害、替换、减免、结算后触发及事件顺序；
- 公开状态、玩家私密状态与“有人可响应”类侧信道的界限；
- 15 秒超时、60 秒持续断联、默认放弃和强制随机合法项；
- 服务端种子随机、命令幂等、JSON 往返和重放一致性。

每个规则争议使用独立决策记录：问题、最小场景、C# 行为与位置、数据库/说明证据、可选解释、结论和受影响场景。交互工作时可由维护者裁定；无人值守 `/goal` 中按 [GOAL_CONTRACT.md](../../GOAL_CONTRACT.md) 作出可追踪的临时裁定后继续。

## R-05：用原型验证交互，不等规则写完

这个项目的 UI 风险不是颜色不够好看，而是六名玩家、大量手牌/技能和嵌套等待在桌面与手机上无法清楚操作。因此先用模拟数据制作可点击原型，至少覆盖：

- 六人座位、队伍关系、当前回合与等待对象；
- 自己回合、一个/多个目标、大量手牌与大量技能；
- 冰心诀响应链、逐次放弃与作用范围说明；
- 多人濒死、当前救援对象和下一顺序；
- 剩余时间、超时结果、断联、重连和状态过期；
- 长文本、错误操作、网络延迟和游戏结束。

桌面至少用 1366×768，手机至少用 360×800。通过不以“原型能点”为准，而是浏览器轨迹、布局断言和独立视觉检查能证明：当前在等谁、玩家能做什么、放弃的范围和超时后果均可理解。维护者之后的审美反馈不阻塞无人值守开发。

## R-06：验证不是最后补测试

验证方向已在 [10-verification-strategy.md](10-verification-strategy.md) 形成提案。可填写的[工作节点契约](templates/work-node.md)、[验证收据](templates/verification-receipt.md)和[规则决策记录](templates/rule-decision.md)已建立。正式开发前还要用技术探针实际试填，确认字段足够而不臃肿：

- 黄金场景格式：初始状态、种子、命令、预期事件、六份玩家视图和证据等级；
- 验证收据格式：提交、命令/退出码、随机种子、轨迹、截图/trace 与未覆盖风险；
- 工作节点契约：目标、前置、证据、允许/禁止范围、验收门和停止原因；
- 失败留存：每个随机或并发失败都能保存并用一条命令重放。

测试分工保持不变：纯引擎和属性测试提供大量确定性覆盖；六个策略 Bot 探索长局；Playwright 六个独立 BrowserContext 验证关键用户流程；本机可见浏览器专门验收 UX。LLM Bot 等 `availableActions` 和重放都稳定后再考虑，不充当规则裁判。

## R-07：三个技术探针的止损规则

三个探针的场景已在 [11-technical-route-review.md](11-technical-route-review.md) 定义。每个探针必须单独提交验证收据，并遵循：

- 嵌套续算不能在每个等待点 JSON 往返后保持一致：停止卡牌迁移，重新评估状态机模型与 TypeScript/.NET 路线；
- 六份玩家视图出现私密信息或侧信道泄露：重做服务端投影契约，不在 UI 层隐藏字段补漏；
- 恢复后的结果、随机或超时与未重启分支不一致：先修正命令/事件边界，不继续增加内容。

探针通过只证明路线足以承载正式开发，不等于已完成 MVP。

## 可以明确推迟的事

## R-08 复核问题

只有当下列问题均能用产物回答时，才开始第一个正式工作节点：

1. 我们要迁移的每个内容是什么，它的 C#/数据库来源在哪里？
2. 旧行为能否重放？不能时用什么证据等级和自主裁定策略代替？
3. 冰心诀、多人濒死、超时和断联的最小场景是否已经无歧义？
4. 桌面和手机玩家能否不靠猜测完成这些场景？
5. 三个探针能否从任意等待点恢复，并给出六份不泄密的视图？
6. 任何失败能否依靠固定种子和日志复现，而不是再次等它偶然发生？
7. 要公开推送的历史是否不包含无权分发、秘密或不必要的大对象？
8. 第一个工作节点是否有目标、前置、允许范围、验收命令和停止条件？

任何一项只能用“AI 应该能处理”、“以后再补”或“看起来差不多”回答，都是 No-Go。
