# CS02 英雄技能迁移

CS02 按“归属图 → 通用机制 → 单个真实技能闭环”的顺序迁移，不先造一套无法证明正确的万能技能 DSL。英雄与技能的静态归属来自生成目录中每个英雄的 `dependencies.contentIds`，引擎内完整保存 34 名当前范围英雄、77 条技能归属边（76 个不同技能），并由 `hero-skills:contract` 逐边比对。

## 第一闭环：JN50402 剑匣

- 所属英雄：`xyy.hero.xj404` 慕容紫英。
- C# 的 `G0IS` 在装载原生技能时触发 `JN50402Action(type=1)`，执行 `TuxLimit += 2`；默认上限 3，因此最终上限为 5。
- `G0QR` 分支只负责在弃牌检查时显示技能，真正的裁决仍是“手牌数大于当前上限才弃牌”。
- 新引擎在六人选将全部完成时，根据权威 `heroId` 原子计算手牌上限；五张不弃，六张弃一。服务端状态和玩家投影公开上限，但仍只向本人公开手牌实体。
- 该被动没有选择、响应或超时窗口；其结果随状态快照、事件回放和 SQLite 恢复保持确定。

`JN50402` 已闭合；此时慕容紫英仍为 partial，因为 `JN50401` 赠剑尚未迁移。今后若某个已迁移规则能改变英雄或动态获得/失去技能，该节点必须复用技能派生属性重算后才能验收，不能只改客户端显示。

## 第二闭环：JN50501 凝冰焚炎

- 所属英雄：`xyy.hero.xj405` 玄霄。
- C# 的 `Valid` 要求批次中至少有一个以自己为目标的正数水/火项目；一旦触发，`Action` 会删除该批次内全部以自己为目标、没有 `IMMUNE_INVAO` 的水/火项目，包括同批的零值项目。只有零值项目时不触发。这个略显奇怪的批次行为按旧实现保留。
- 新引擎在替换、加减值完成并确定最终目标后、响应窗口开启前应用该被动。混合批次中只移除匹配项目，不影响其他玩家或雷/无属性伤害。
- 普通水火项目被移除后不开放隐蛊窗口；`IMMUNE_INVAO` 火伤仍进入正常隐蛊/冰心诀链，并能跨 JSON 检查点与 SQLite 重启继续。

`JN50501` 已闭合；玄霄仍为 partial，因为 `JN50502` 结拜及其战斗命中修正尚未迁移。

## 第三闭环：JN20202 拒绝

- 所属英雄：`xyy.hero.xj202` 苏媚。
- C# 先复用普通 TP01 的合法性判断，再只允许从自己的特殊类（`TuxType.TP`）手牌中选择一张作为冰心诀支付；普通技牌、战牌和装备均不合法。
- 协议用独立的 `play-skill-converted-reaction-card` 明确携带物理支付牌、技能 ID 和目标效果。服务端事件保留支付来源，子效果复用普通冰心诀的 `cancel-effect` 节点，因此反制、全员放弃、父窗口恢复和奇偶结算不另写一套状态机。
- 该动作只投影给当前优先持有者；15 秒超时仍是放弃，不支付手牌。JSON 检查点和 SQLite 重启可从转换后的子窗口继续。

`JN20202` 已闭合；苏媚仍为 partial，因为 `JN20201` 尚未迁移。

## 第四闭环：JN40301 烹饪

- 所属英雄：`xyy.hero.x3w03` 星璇。
- SQLite 同时登记 `TP02` 的行动模式与濒死模式；C# 要求从自己的手牌中选择任意两张，再把两张物理牌一并交给普通 TP02 处理。濒死触发的 `Valid(type=1)` 本身未重复检查手牌数，但输入器不足两张时没有合法选择，新引擎直接不开放动作，结果一致。
- 玩家投影只给原生星璇提供一个选择器：候选是自己的全部手牌、必选两张，避免按组合枚举造成动作数量平方增长。服务端仍校验恰好两张、互异、均在本人手牌中，不能伪造技能、目标或卡牌。
- 行动阶段生成与普通灵葫仙丹相同的 `card:xyy.card.tp02` 效果，因此可被冰心诀响应，支付来源和技能 ID 保留在事件中；濒死阶段复用既有救援优先级、治疗规划、装备修正和轮转，不开放额外旁路窗口。
- 两种使用都是可放弃操作：行动窗口超时结束行动，救援窗口超时 pass，均不会预先支付手牌。JSON 回放与六 WebSocket 的 SQLite 重启覆盖两张牌的原子支付和私密动作隔离。

`JN40301` 已闭合；星璇仍为 partial，因为 `JN40302` 尚未迁移。

## 第五闭环：JN20302 元灵归心术

- 所属英雄：`xyy.hero.xj203` 沈欺霜。
- SQLite 将其登记在自己的技牌阶段且不限制次数；C# 每次只允许选择一张 `TuxType.JP` 手牌和任意一名在场玩家，先弃置物理牌，再直接调用 `Cure(..., 2)`。没有 `G0CC` 卡牌效果消息，因此不开放冰心诀响应。
- 新协议使用窄的 `activate-hero-skill` 命令携带技能 ID、所选物理牌和目标；玩家投影给出本人的 JP 候选、所有存活目标及各自必选数量。服务端拒绝非 JP、外来/多张牌、伪造技能、越权角色和死亡目标。
- 弃牌与治疗属于同一个可重放事件；治疗沿用统一的 HP 上限和天蛇杖等修正。只要仍持有 JP 手牌，动作会继续开放，保持旧版“每丢弃 1 张”的可重复语义。
- 该技能是可放弃行动，15 秒超时结束行动而不支付手牌。JSON 回放、SQLite 重启和六 WebSocket 验证了支付、治疗结果与动作私密性。

`JN20302` 已闭合；沈欺霜仍为 partial，因为战斗相关的 `JN20301` 尚未迁移。

## 第六闭环：JN40401 饕餮

- 所属英雄：`xyy.hero.x3w04` 王蓬絮。
- C# 的候选来自 `ListOutAllCards()`，即自己的手牌、武器和防具；每次选一张，先发 `G0QZ` 弃置，再直接治疗自己 2 HP。技能未限制次数，只要仍有任意可支付牌就能继续发动。
- 玩家投影按手牌、武器、防具给出候选且固定目标为本人；服务端记录真实来源区域，拒绝外来牌、多张牌、伪造技能、错误目标或非本人行动阶段。
- 新引擎先构造移除支付牌后的状态，再调用统一治疗规划。这保留了关键顺序：若支付天蛇杖，本次只有基础治疗 2；若支付其他牌并保留天蛇杖，本次治疗为 3。支付防具同样先清空装备槽。
- 结算不开放冰心诀窗口；行动超时不支付牌。JSON 回放和六 WebSocket 的 SQLite 重启覆盖装备支付、HP、区域守恒与动作私密性。

`JN40401` 已闭合；王蓬絮仍为 partial，因为 `JN40402`、`JN40403` 尚未迁移。

## 第七闭环：JN50201 搜囊探宝

- 所属英雄：`xyy.hero.xj402` 韩菱纱。
- SQLite 将技能登记为自己的技牌阶段、每阶段一次；C# 要求本人至少有一张手牌且至少一名其他玩家仍有牌，随后选择一张本人手牌和【偷盗】或【铜钱镖】，通过 `G0CC` 进入普通卡牌结算。
- 玩家投影给出本人全部手牌作为单张支付候选，并分别投影 JP01 的有手牌对手、JP06 的可弃牌目标。JP06 的本人目标按支付后的状态判断，避免把唯一手牌既当支付又当可弃目标；服务端重新校验所有来源、模式、目标和原生归属。
- 转换事件同时记录物理支付牌、技能 ID 和虚拟卡牌 ID，物理牌立即进入弃牌堆。之后完全复用普通 JP01/JP06 的冰心诀窗口、不透明手牌槽、装备选择、确定性强制超时与效果恢复；冰心诀抵消后不会打开选牌，但本阶段次数仍已消耗。
- 当前回合序列化保存 `usedSkillIds`，服务重启后仍禁止再次发动，新回合才清空。行动阶段 15 秒超时属于未发动并且不支付牌。
- JSON 回放覆盖窗口和强制选择；六个真实 WebSocket 分别在响应窗口、隐藏选牌中重启 SQLite 服务，验证次数状态、目标装备、私密动作和不透明选项均正确恢复。

`JN50201` 已闭合；此时韩菱纱仍为 partial，因为 `JN50203` 尚未迁移。

## 第八闭环：JN50202 劫富济贫

- 所属英雄：`xyy.hero.xj402` 韩菱纱。
- SQLite 将其登记为自己的技牌阶段、每阶段一次；C# 先发送 `G0DH` 摸一张，再读取摸牌后的 `Tux.Count`，达到两张才发送一次强制弃牌。即使牌堆和弃牌堆都无法提供牌，阈值仍按实际手牌数判断。
- 玩家投影给原生韩菱纱一个零支付、零目标动作。服务端复用统一的确定性摸牌/弃牌堆洗回规划，并在同一个权威事件中记录摸牌结果、消耗本回合次数；摸后少于两张直接结束，达到两张则创建可序列化的本人强制选择。
- 选择只向本人公开全部当前手牌实例，恰好弃一张；其他五名玩家只能看到公开手牌数量和无私密牌 ID 的技能效果。该技能不产生卡牌效果或冰心诀响应窗口。
- 强制选择的 15 秒超时从合法手牌中使用可重放种子随机弃一张；未发动时的行动超时仅结束行动。JSON 回放和六个真实 WebSocket 分别验证了选择中重启、最终状态重启、次数状态与隐藏信息隔离。
- 旧 `G0DH` 会排除 `Board.ProtectedTux`。当前标准包+凤鸣玉誓范围内没有保护牌生产者；已知来源是范围外特殊英雄 SP301 的技能，因此本闭环只声明当前范围完整，不声称兼容特殊英雄扩展。

`JN50202` 已闭合；此时韩菱纱仍为 partial，因为死亡触发技能 `JN50203` 尚未迁移。

## 第九闭环：JN50203 盗墓

- 所属英雄：`xyy.hero.xj402` 韩菱纱。
- SQLite 将其登记在 `!G0ZW` 死亡批次、优先级 190、每次触发一次；C# 在优先级 100 先标记整批死亡和胜负，若韩菱纱也在本批死亡或本批已直接决定胜负则不会进入盗墓。否则它在优先级 200 的通用死亡弃牌前收取所有其他阵亡角色的手牌、武器和防具。
- 服务端把同时死亡作为一个可序列化批次：先完成全部救援和死亡标记，再一次性把所有阵亡牌区移入原生韩菱纱的手牌。装备收取后成为普通手牌；阵亡玩家的公开装备槽和手牌计数同时清空。没有牌的死亡批次仍走统一清理，但不触发技能。
- 收取后仅韩菱纱收到捕获牌实例、可分配动作和 15 秒期限。她可反复选择任意非空子集并交给任意其他存活玩家，每次分配重开 15 秒；也可随时结束并保留所有未分配牌。其他五席只看到公开手牌数量变化，不会从 `pendingChoice`、`availableActions` 或阵亡牌区看到捕获牌 ID。
- 可放弃窗口超时或断联自动决策均直接结束，不再随机分牌。无论分完还是提前结束，每个死亡批次只造成一次普通中性自身伤害；该伤害复用统一 TP03/FJ05 响应和伤害/濒死管线，因此可以被合法响应，也可以再次引发濒死批次。
- 旧 `G0HQ` 会排除 `Board.ProtectedTux`；与 JN50202 相同，当前标准包+凤鸣玉誓没有保护牌生产者，因此本闭环验证范围内的全部阵亡牌均可收取，但不外推到特殊英雄扩展。
- 单元场景覆盖单人死亡、两人同时死亡、本人同批死亡和死亡已决胜四种边界；JSON 回放覆盖分配、重启、系统超时及自伤响应；六个真实 WebSocket 覆盖私密动作、收取选择重启、部分分配、自伤窗口再次重启及最终牌区。

`JN50203` 已闭合；韩菱纱的基础身份和三个原生技能均为 verified。

## 第十闭环：JN50401 赠剑

- 所属英雄：`xyy.hero.xj404` 慕容紫英。
- SQLite 将其登记为自己的技牌阶段、可反复发动；C# 候选为本人装备区中的装备和其他在场角色，并用阶段内 `RAM.Present` 记录已经赠送过的目标。进入技牌阶段时全员 RAM 会清空，所以限制是“本技牌阶段同一目标一次”，而不是整局或技能总次数。
- 每次发动恰好选择一件当前装备和一名尚未获赠的其他存活玩家。权威事件先从慕容紫英装备槽移除该实体牌，再装入目标的同类槽；当前范围只有单个武器槽和防具槽，因此目标原有同槽装备立即进入弃牌堆。随后独立的统一摸牌事件补两张，保留“先替换、后摸牌”的旧顺序；牌堆不足时，新弃置的被替换装备可以进入确定性洗回并成为第二张牌。
- 阶段内的已赠目标集合保存在可序列化 `turn.usedSkillTargetIds`；SQLite 重启后同一目标仍被排除，换目标可以继续发动，新回合创建时该字段清空。只要没有装备或没有未用目标，动作就不再投影。
- 装备转移、替换弃牌和各玩家手牌数量是公开信息；补到的两张牌 ID 只进入慕容紫英本人的手牌投影。技能不创建卡牌效果或冰心诀窗口；15 秒行动超时属于未发动，不移动装备也不摸牌。
- 旧 `ListOutAllEquips` 还理解额外装备和假装备；当前标准包+凤鸣玉誓运行时只有物理武器、防具槽且没有假装备生产者，本闭环不声称兼容范围外特殊牌区。
- 单元测试覆盖同目标拒绝、换目标重复、伪造手牌/未知牌拒绝、行动超时、同槽替换和替换牌参与洗回；JSON 回放覆盖两次转移与目标历史；六个真实 WebSocket 覆盖首次转移、阶段中重启、重复目标拒绝、第二次转移、最终重启及五份补牌隐私投影。

`JN50401` 已闭合；慕容紫英的基础身份和两个原生技能均为 verified。

## 第十一闭环：JN40302 兄弟

- 所属英雄：`xyy.hero.x3w03` 星璇。
- SQLite 将其登记为自己的技牌阶段、每阶段一次；C# 的合法性检查把本人也计入“有手牌的同队角色”，发动后则只收取其他存活队友的全部手牌。星璇原有手牌保留并与收取牌一起进入后续分配候选，装备区、对手牌区均不移动。
- 旧 `G0HQ` 对每名队友执行整手转移并使用进程随机洗牌；该顺序既不影响所有权又无法稳定重放。新引擎明确采用座次顺序、再按各来源手牌顺序追加，作为保守且确定性的临时裁定；卡牌守恒与可选分配集合保持一致。
- 收取和阶段内一次标记在同一个权威事件中完成。仅星璇看到完整候选、分配动作与 15 秒期限；她可反复选择任意非空子集交给任意其他存活队友，每次成功分配重开 15 秒。其他五席只看到公开手牌数量变化，不会从选择、动作、日志或错误中得到牌 ID。
- 尽管描述写“分配所有手牌”，C# 的输入 `0`、`/0` 或空输入会立即退出循环，因此保留可随时提前结束并留下全部未分配牌的真实行为。超时或断联自动决策也直接结束；没有不可放弃步骤，不进行随机分牌，不创建卡牌效果或冰心诀窗口。
- 旧 `G0HQ` 会排除 `Board.ProtectedTux`；当前标准包+凤鸣玉誓没有保护牌生产者，因此本闭环收取当前范围内全部队友手牌，但不声称兼容范围外特殊英雄。JSON 回放覆盖部分分配和超时；六个真实 WebSocket 覆盖私密收取、选择中重启、部分分配、过期选择重启自动结束、次数状态与最终牌区恢复。

`JN40302` 已闭合；星璇的基础身份和两个原生技能均为 verified。
