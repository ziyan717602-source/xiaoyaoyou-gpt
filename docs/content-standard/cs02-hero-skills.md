# CS02 英雄技能迁移

CS02 按“归属图 → 通用机制 → 单个真实技能闭环”的顺序迁移，不先造一套无法证明正确的万能技能 DSL。英雄与技能的静态归属来自生成目录中每个英雄的 `dependencies.contentIds`，引擎内完整保存 34 名当前范围英雄、77 条技能归属边（76 个不同技能），并由 `hero-skills:contract` 逐边比对。

## 第一闭环：JN50402 剑匣

- 所属英雄：`xyy.hero.xj404` 慕容紫英。
- C# 的 `G0IS` 在装载原生技能时触发 `JN50402Action(type=1)`，执行 `TuxLimit += 2`；默认上限 3，因此最终上限为 5。
- `G0QR` 分支只负责在弃牌检查时显示技能，真正的裁决仍是“手牌数大于当前上限才弃牌”。
- 新引擎在六人选将全部完成时，根据权威 `heroId` 原子计算手牌上限；五张不弃，六张弃一。服务端状态和玩家投影公开上限，但仍只向本人公开手牌实体。
- 该被动没有选择、响应或超时窗口；其结果随状态快照、事件回放和 SQLite 恢复保持确定。

`JN50402` 已闭合；慕容紫英仍为 partial，因为 `JN50401` 赠剑尚未迁移。今后若某个已迁移规则能改变英雄或动态获得/失去技能，该节点必须复用技能派生属性重算后才能验收，不能只改客户端显示。

## 第二闭环：JN50501 凝冰焚炎

- 所属英雄：`xyy.hero.xj405` 玄霄。
- C# 的 `Valid` 要求批次中至少有一个以自己为目标的正数水/火项目；一旦触发，`Action` 会删除该批次内全部以自己为目标、没有 `IMMUNE_INVAO` 的水/火项目，包括同批的零值项目。只有零值项目时不触发。这个略显奇怪的批次行为按旧实现保留。
- 新引擎在替换、加减值完成并确定最终目标后、响应窗口开启前应用该被动。混合批次中只移除匹配项目，不影响其他玩家或雷/无属性伤害。
- 普通水火项目被移除后不开放隐蛊窗口；`IMMUNE_INVAO` 火伤仍进入正常隐蛊/冰心诀链，并能跨 JSON 检查点与 SQLite 重启继续。

`JN50501` 已闭合；玄霄仍为 partial，因为 `JN50502` 结拜及其战斗命中修正尚未迁移。
